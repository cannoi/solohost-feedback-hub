## Architecture and API boundaries

- `server.js` owns HTTP routing, session/auth checks, body parsing, public/admin API routing, event ingestion, and AI mounts.
- `lib/store.js` implements the JSON-file store; `lib/settings.js` stores admin settings and password hashes; `lib/classify.js` defines legacy feedback categories/statuses; insights and feedback/AI modules are otherwise reusable.
- Existing APIs are unversioned (`/api/health`, `/api/session`, `/api/login`, `/api/feedback`, `/api/notices`, `/api/updates`, `/api/apps`, `/api/admin/overview`, and AI/settings routes). No formal OpenAPI contract found.
- No relational database, migrations, tenant credential registry, scope model, OAuth, webhook subscription/delivery queue, or integration request audit trail found.

## Material limitations and security concerns to resolve before production use

- Payment ingestion stores an event as `confirmed` from request data; it does not call Pi Platform for server-side verification or completion. This must not be represented as Pi payment settlement.
- `server.js` contains a hard-coded fallback ingest token. Deployments should require explicit secrets and safely rotate them.
- Public API CORS is wildcard. API credentials are a single shared ingest token rather than per-app scoped credentials; `ensureApp` auto-creates app IDs from incoming payloads.
- Sessions are process-memory only; the cookie lacks `Secure` handling for HTTPS deployments. Rate limits are per-process memory.
- The JSON store has no cross-process transaction/locking, schema migration, foreign keys, or durable background-job model. Concurrent writes can overwrite one another.
- Feedback can store app supplied IDs, but there is no customer identity model or tenant authorization boundary for admin reads beyond the single platform login.
- Existing donation UI supports wallet/address and bank transfer instructions; it is not an official Pi SDK payment flow.
- Existing tests do not cover HTTP integration, tenant isolation, webhook delivery, auth scopes, or official Pi payment handling. No claim of production readiness is warranted from current checks.

## Reusable modules

- Preserve existing routes and payloads for backwards compatibility.
- Extend `lib/store.js` behind its current interface where possible; retain JSON format compatibility during a storage transition.
- Reuse password hashing/settings, feedback classification and insights, existing public form/client SDK, notices and release updates, and Docker volume conventions.
- Keep the native Node modular-monolith architecture unless an explicitly approved design changes that choice.

## Suggested milestones for review

1. Foundation: app registry, per-app credentials/scopes, versioned health and feedback API, tenant boundaries, request validation/rate limits, migration-safe persistence.
2. Feedback operations: admin replies/history, filters/pagination, attachment constraints, owner/customer follow-up, analytics and embeddable widget.
3. Notifications and webhooks: app-scoped notification API, event records, HMAC signatures, idempotency, delivery retries/logs and manual retry.
4. Pi payment: official SDK handoff + server-only Pi Platform verification/completion, transaction state machine/idempotency/audit; sandbox-only verification before any completion claim.
5. Owner dashboard, SoloHost integration kit, documentation, deployment and security review.
