# Pi payment integration

Feedback Hub now includes a tenant-bound U2A (user-to-app) payment workflow backed by the documented Pi Platform API. The Hub stores per-application Developer App configuration, verifies Pi user identity, approves only a matching payment, accepts completion only after authoritative Pi transaction verification, and reconciles interrupted server requests. No private keys or wallet credentials are collected.

The implementation follows the [official Pi payment guide](https://developers.minepi.com/docs/accept-payment/Payments) and [Platform API reference](https://developers.minepi.com/docs/api-reference/PlatformAPI). They specify that the Pi SDK runs in the supported frontend, while the backend calls `GET /v2/payments/{payment_id}`, `POST /v2/payments/{payment_id}/approve`, and `POST /v2/payments/{payment_id}/complete` using `Authorization: Key …`. User identity is validated using `GET /v2/me` with that user's bearer access token. The Hub does not use undocumented endpoints.

## Configure an application

1. Register and obtain admin approval for the connected application.
2. Create/authorize its Pi app in the Pi Developer Portal for the intended network. Configure the official Pi SDK app in that application's own frontend.
3. In Feedback Hub, sign in as the application owner or admin and open **Pi payments**.
4. Enter the Pi Developer App ID, `testnet` or `mainnet`, and that app's Pi Server API key. The Hub encrypts the key using `HUB_ENCRYPTION_KEY`. The key cannot be read back; rotate by saving a replacement.
5. Issue an application API credential with `payments:create`, `payments:read`, `fees:create`, and `fees:read`; store it in the connected application's backend secret store.

The master encryption key is generated by `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"`. Store it outside the repository and persist it securely across restarts and backups. Losing it makes encrypted app secrets unusable. Rotating it requires an operator-controlled re-encryption migration; simply replacing it is not supported. Do not send keys in chat, commit them, or expose them to browser code.

## Payment lifecycle

1. The connected app backend first creates a provider-neutral fee order with `POST /api/v1/fees/orders`, using `provider:"pi"`, `currency:"PI"`, `amount_scale:7`, and the exact amount in `amount_subunits`. It then creates a Hub session with `POST /api/v1/payments/create`, passing that `fee_order_id`, the same Pi amount, a unique `Idempotency-Key`, order reference, memo, and metadata. The Hub rejects a mismatched, cross-app, already-bound, or non-pending fee order. Returned `session_id`, `fee_order_id`, and `metadata.hub_session_id` are server-bound payment context.
2. The connected app's Pi-enabled frontend authenticates the user with `payments` permission and starts `Pi.createPayment` with the returned amount, memo, and metadata.
3. On `onReadyForServerApproval(paymentId)`, the frontend sends the payment ID and Pi user `accessToken` to its own backend. That backend calls `POST /api/v1/payments/{session_id}/approve` with its Hub application credential and body `{ "payment_id": "…", "user_access_token": "…" }`. The Hub checks `/me`, fetches the payment using the configured Pi Server API key, checks the app-bound user UID, exact amount, memo, metadata, direction, and cancellation state, then calls Pi approval. The access token is used for the identity request and is not persisted.
4. Pi SDK lets the user sign the transaction. On `onReadyForServerCompletion(paymentId, txid)`, the connected backend calls `POST /api/v1/payments/{session_id}/complete` with `{ "payment_id": "…", "txid": "…" }`.
5. The Hub refetches authoritative payment state, validates `transaction_verified`, `transaction.verified`, matching txid and developer approval, then asks Pi Platform to complete. Only a successful authoritative completion response changes the state to `completed` / `verified`, reconciles the linked fee order from that verified Pi result, and queues `payment.completed` to that application's webhook. The payment response exposes `service_delivery_allowed`; a linked order is eligible only when the fee ledger reports `paid` and `verified`.
6. If an HTTP request is interrupted after Pi has acted, the durable reconciler re-fetches the official payment and recovers `approving` or `completion_pending` sessions. Repeat requests for the same payment/txid are idempotent; a different payment ID or txid is rejected.

```js
// In the connected app's Pi Browser frontend (illustrative; order data comes from its backend)
Pi.init({ version: "2.0", sandbox: true });
const auth = await Pi.authenticate(["username", "payments"], async payment => {
  // Send payment.identifier to your backend for Hub session reconciliation.
});
const session = await fetch("/api/orders/42/pi-session", { method: "POST" }).then(r => r.json());
Pi.createPayment({ amount: session.amount, memo: session.memo, metadata: session.metadata }, {
  onReadyForServerApproval: paymentId => fetch("/api/orders/42/pi/approve", {
    method: "POST", headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ session_id: session.session_id, payment_id: paymentId, access_token: auth.accessToken })
  }),
  onReadyForServerCompletion: (paymentId, txid) => fetch("/api/orders/42/pi/complete", {
    method: "POST", headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ session_id: session.session_id, payment_id: paymentId, txid })
  })
});
```

The example browser talks to its own backend, not directly to Feedback Hub: the app API credential stays server-side and the Hub user access token must not be logged. The originating app updates its order only after its backend receives `completed` with `verification_state: "verified"` or verifies the signed `payment.completed` webhook.

## QR checkout verification

The official [Pi payment guide](https://developers.minepi.com/docs/accept-payment/Payments), [Client SDK reference](https://developers.minepi.com/docs/api-reference/SdkReference), and [Platform API reference](https://developers.minepi.com/docs/api-reference/PlatformAPI) describe U2A checkout through `Pi.createPayment` and its server-approval / server-completion callbacks. The reviewed SDK reference lists authentication, payment, native features, sharing, and URL-opening methods; it does not document a static QR payment method or a QR scan result that verifies payment. A QR code can at most navigate a customer to an app or display an address; it is not evidence that a specific order was paid. This Hub therefore treats QR scans or client callbacks as untrusted and never settles an order from them. If a product chooses to offer a QR for navigation, checkout must still run through the official SDK and server-confirmed Platform API flow above. No standalone static QR checkout is claimed or implemented.

## API response and status meanings

- `created`: local Hub session exists; no Pi payment is verified.
- `approving`: server approval is in progress or awaiting reconciliation.
- `approved`: Pi developer approval succeeded; this is **not** transaction verification or completion.
- `completion_pending`: Pi transaction was authoritatively verified and the server completion is in progress or awaiting reconciliation.
- `completed` with `verification_state: verified`: Pi Platform confirmed developer completion and transaction verification.
- `failed`: authoritative cancellation or terminal outcome; inspect the safe `failure_code`.

Pi session creation alone returns `verification_state: unverified`. SDK callbacks, client-supplied txids, or HTTP success from the originating app are never proof. Payment audit entries are append-only. Pi transaction completion does not imply an external exchange, cash-out, refund, or settlement guarantee.

## Sandbox / production boundary

Unit and HTTP tests use a mock Pi Platform and never contact the Pi network. The connector sample implements the official SDK flow and sets Sandbox mode; this workspace has no operator-authorized Pi Developer App ID, Server API key, Pi Browser session, or Sandbox configuration, so no real Sandbox transaction or QR/device behavior was verified. Before enabling an app, the operator must configure its own approved Pi Developer App and testnet credentials in the owner dashboard, run the complete workflow in the Pi Sandbox environment, and verify approval, user signing, completion, cancellation, interrupted recovery, and webhook processing. Mainnet activation requires the connected app's own Pi eligibility and configuration. **Production Pi payment readiness is not verified by this repository session.**

Pi does not document a general U2A refund endpoint in the referenced flow; the Hub does not claim to refund Pi payments. Refunds or cancellations outside the documented developer approval/completion lifecycle need an officially supported Pi capability and separate operator review.
